## 결정과 제품 조건

**새 화면의 기본은 CSS Modules + React Context + CSS 변수**로 제안합니다. 제품 요구는 공통 기본값과 브랜드별 배경색을 포함한 등록 브랜드의 색상·글꼴 전환이고, 우선 기준은 개발 중 수정과 빌드 속도입니다. 네 후보는 하나의 공통 토큰 정의와 브랜드별 오버라이드로부터 같은 최종 테마를 받습니다. 새 모달 토큰을 연결할 때 CSS Modules는 후보별로 한 곳을 수정했고, 초기 JS·CSS 합계는 가장 작았고, 브랜드 전환이 CSS 규칙을 추가하지 않았습니다. 빌드 시간의 범위가 크게 겹쳤으므로 속도 차이만으로 후보를 고르기 어렵습니다.

| 후보 | 초기 JS+CSS gzip | 토큰 분리 전 대비 | CSS Modules 대비 | 새 모달 토큰 수정 파일 / 지점 | 처음 보는 브랜드의 생성 규칙 | 우선 검토할 조건 |
|---|---:|---:|---:|---:|---:|---|
| **CSS Modules + React Context** | 76,785 B | +355 B | 기준 | 1 / 1 | 0 | 공통 DS를 유지하며 의존성과 수정 범위를 작게 가져갈 때 |
| **styled-components** | 86,960 B | +350 B | +10,175 B (+13.3%) | 1 / 1 | +73 | 기존 코드가 이미 사용 중이거나 컴포넌트 props로 스타일 규칙 자체를 계산해야 할 때 |
| **Tailwind CSS** | 80,599 B | +349 B | +3,814 B (+5.0%) | 2 / 2 | 0 | 팀에 Tailwind 토큰·유틸리티 규칙과 작성 경험이 있을 때 |
| **shadcn/ui + Tailwind CSS** | 94,830 B | +364 B | +18,045 B (+23.5%) | 공유 2 / 2, shadcn 전용 0 / 0 | 0 | 도입할 컴포넌트를 목록으로 확인했고 기존 DS에 맞추는 비용보다 재사용 가치가 클 때 |

gzip 크기는 각 HTML이 초기에 참조하는 자산을 합산한 값입니다. 토큰 분리 전 수치는 `9445b23`에 기록한 기준입니다. 운영 전송량과 첫 화면 렌더 시간은 별도 지표입니다. 수정 파일과 지점은 공통 토큰 정의를 제외한 값이며, 모달은 네 후보에서 공통 구현입니다. 새 브랜드가 기존 토큰을 사용하면 디자인 시스템의 `brands.ts`에서 오버라이드를 정의하고 공통 데모 계정 매핑에 계정을 추가합니다. 자세한 샘플과 측정 조건은 아래와 [빌드·개발 반영·런타임 측정](build-runtime.md)에 있습니다.

## 공통 토큰에서 브랜드 화면까지

| 위치 | 책임 |
|---|---|
| [tokens.ts](../../../experiments/brand-theme/shared/design-system/tokens.ts) | 페이지·카드 배경, 텍스트, 경계선, 강조색, 본문 글꼴과 컨트롤·카드 모서리의 공통값 |
| [brands.ts](../../../experiments/brand-theme/shared/design-system/brands.ts) | 이름·이니셜과 브랜드별 변경값. TypeScript로 페이지 배경, 강조색 계열, 본문 글꼴만 오버라이드 허용 |
| [theme.ts](../../../experiments/brand-theme/shared/design-system/theme.ts) | 공통값에 브랜드 변경값을 합쳐 최종 테마를 계산하고 CSS를 쓰는 후보에 `--ds-*` 변수 제공 |

공통 대시보드는 **계정 → env → Grove** 순으로 브랜드를 정하고 최종 테마를 전달합니다. Grove는 오버라이드를 비워 공통 토큰을 모두 상속합니다. 네 가지 후보는 각각 CSS Modules의 React Context, styled-components의 `ThemeProvider` 보간, Tailwind 유틸리티 매핑, shadcn/ui의 시맨틱 클래스 매핑을 유지합니다. 페이지 레이아웃과 상태별 배지 스타일은 후보별 구현에 둡니다.

Chrome 회귀 테스트는 네 후보에서 같은 응답 두 곳을 임시로 바꿔 확인합니다. 공통 테두리 `#e1e7e3 → #324c76`은 모든 브랜드의 카드에 반영됐고, Signal의 페이지 배경 `#edf0ff → #dde8ff`는 Signal에만 반영됐습니다. Grove의 공통 배경과 Ember의 지정 배경, 카드 표면 및 모서리 값도 확인했습니다.

## 공통 배경과 브랜드 지정 배경

| 브랜드 | 페이지 배경 | 선택 경로 |
|---|---|---|
| Grove | 공통 기본값 `#f5f7f6` | 브랜드 배경을 생략해 공통값 적용 |
| Signal | 옅은 블루 바이올렛 `#edf0ff` | 브랜드의 `pageBackground` 사용 |
| Ember | 옅은 피치 `#fff1e8` | 브랜드의 `pageBackground` 사용 |

배경 토큰은 대시보드 페이지 영역에 적용합니다. CSS Modules와 Tailwind 계열은 `--ds-color-page`를 참조하고, styled-components는 같은 최종 테마의 `color.page`를 보간합니다. 상단의 **Page background** 문구에서 적용 출처를 확인할 수 있습니다. 네 후보에서 계정 변경과 로그아웃, 새로고침 후의 계산된 배경색을 검증했습니다.

## 후보별 판단 근거

### CSS Modules + React Context

- **채택 근거** — 클래스 이름을 파일 단위로 스코프하고 테마 색상·글꼴은 CSS 변수로 전달합니다. React와 공통 도구 외에 후보 전용 의존성이 없습니다. 일반 CSS로 작성하므로 기존 DS의 토큰과 셀렉터를 옮기기 쉽습니다. [Vite CSS Modules](https://vite.dev/guide/features.html#css-modules)
- **유지보수 비용** — 버튼·카드·배지의 변형과 상태, 포커스 스타일을 직접 설계하고 검증합니다. 공유 컴포넌트나 변형 규칙이 부족하면 화면별 CSS와 중복 정의가 늘어납니다. 파일 단위 클래스 스코프를 적용해도 `:global`, 문서 전역 리셋, 상속되는 CSS 변수의 범위는 별도로 관리해야 합니다.
- **전환 비용** — 토큰 계약은 다른 후보로 가져갈 수 있습니다. 화면에 적용한 모듈 클래스와 스타일 선언은 목적지 방식에 맞춰 옮겨야 합니다. 상태에 따른 변형과 접근성 검증까지 포함해 이동 비용을 산정합니다.

### styled-components

- **채택 근거** — 타입이 있는 테마와 컴포넌트 props를 스타일 코드에서 직접 참조할 수 있습니다. 이미 라이브러리를 쓰는 제품에서는 새 화면을 기존 컴포넌트와 같은 방식으로 확장할 수 있습니다.
- **런타임 비용** — 실험의 `Region.ts`는 새 브랜드를 처음 방문할 때 CSSOM 최상위 규칙 73개를 추가했고, 재방문에는 기존 규칙을 재사용했습니다. 초기 JS만 CSS Modules보다 12,164바이트 더 컸고, 초기 CSS가 작아 전체 증가분은 10,175바이트였습니다. 보간에서 가능한 값이 많을수록 생성되는 클래스가 늘어날 수 있습니다. 유한한 변형은 고정 클래스나 `data-*` 속성으로, 값만 달라지는 경우는 CSS 변수로 표현할 수 있습니다. 이 대안의 성능은 이번 실험에서 측정하지 않았습니다. [styled-components 성능 가이드](https://styled-components.com/docs/advanced#performance)
- **통합과 전환 비용** — 추가 직접 의존성은 `styled-components` 한 개입니다. SSR 도입 시 프레임워크에 맞춰 스타일 수집과 하이드레이션을 검증합니다. 엄격한 CSP에서 스타일 태그에 nonce가 필요하면 주입 설정이 추가됩니다. 다른 방식으로 옮길 때는 테마 값 외에 props 보간과 스타일을 감싼 컴포넌트 경계를 함께 옮깁니다. [SSR 설정](https://styled-components.com/docs/advanced#server-side-rendering), [CSP nonce 설정](https://styled-components.com/docs/advanced#content-security-policy-csp-nonces)
- **버전 판단** — 측정에는 프로젝트에 설치된 v6.7.0을 사용했습니다. 공식 프로젝트는 2025년 유지보수 모드 전환 이후에도 v6 변경을 배포했고, 확인일 현재 공식 문서는 v7을 알파로 안내합니다. 배포판 지원과 React·프레임워크 호환성은 채택할 버전을 기준으로 확인합니다. [공식 유지보수 이력](https://styled-components.com/blog/celebrating-a-decade-of-styled-components), [v7 상태와 마이그레이션](https://styled-components.com/docs/v7)

### Tailwind CSS

- **채택 근거** — 팀에서 이미 사용하는 유틸리티와 토큰이 있으면 JSX에서 반응형·상태 스타일을 빠르게 조합할 수 있습니다. 정적인 시맨틱 클래스가 브랜드 CSS 변수를 참조하므로, 등록 브랜드의 값 변경은 공통 데이터 수정으로 처리합니다.
- **설정과 격리 비용** — 이 구현은 Tailwind와 Vite 플러그인 두 개를 추가하고, 시맨틱 토큰 매핑과 클래스 탐지 경로를 관리합니다. 동적으로 조립한 클래스 문자열은 빌드에서 탐지되지 않을 수 있습니다. `@source`는 클래스 탐지 범위를 지정합니다. 같은 HTML 문서에 Tailwind와 기존 화면을 함께 넣을 경우 Preflight의 전역 리셋 영향도 별도로 검증합니다. 현재 실험은 후보별 HTML 문서로 격리되어 있습니다. [클래스 탐지](https://tailwindcss.com/docs/detecting-classes-in-source-files), [Preflight](https://tailwindcss.com/docs/preflight)
- **브라우저와 전환 비용** — Tailwind v4의 공식 브라우저 기준은 Chrome 111, Safari 16.4, Firefox 128입니다. 납품 환경이 이 기준을 충족하는지 확인합니다. 도입하거나 걷어낼 때 JSX의 유틸리티 클래스와 토큰 매핑을 수정해야 하므로 공유 컴포넌트 경계에서 전환하면 변경 범위를 줄일 수 있습니다. [Tailwind 호환성](https://tailwindcss.com/docs/compatibility)

### shadcn/ui + Tailwind CSS

- **채택 근거** — Button·Card·Badge처럼 실제 요구와 맞는 컴포넌트의 소스와 사용 패턴을 재사용할 수 있습니다. Tailwind 설정과 토큰을 이미 운영하고 있고, 제공 컴포넌트의 디자인과 상호작용이 제품 요건에 가까울 때 이점이 큽니다.
- **소유와 갱신 비용** — 레지스트리에서 가져온 코드는 프로젝트가 직접 소유합니다. DS에 맞게 토큰, 상태 변형, 기본 트랜지션을 수정할 수 있는 대신, upstream 변경은 CLI diff를 확인하고 로컬 수정과 합쳐야 합니다. 이 구현은 Tailwind 관련 두 개에 `radix-ui`, `class-variance-authority`, `cn`을 더해 후보 관련 직접 의존성이 다섯 개입니다. 다른 컴포넌트를 추가하면 구성은 달라집니다. [shadcn/ui 코드 배포 방식](https://ui.shadcn.com/docs), [CLI diff](https://ui.shadcn.com/docs/cli)
- **검증과 전환 비용** — 버튼의 기본 150ms 전환이 이번 색상 정착 시간에 반영됐습니다. 브랜드별 버튼 상태, 포커스, 대비, 애니메이션 기준은 가져온 디자인과 별도로 확인합니다. 실험의 모달은 공통 React 구현이어서 shadcn Dialog의 구현 속도나 접근성은 비교하지 않았습니다. 외부에 노출한 컴포넌트 props가 유지되면 내부 구현 교체를 점진적으로 진행할 수 있습니다.

## 채택 전 확인할 제품 조건

| 조건 | 이번 실험에서 확인한 범위 | 실제 제품에서 확인할 항목 |
|---|---|---|
| 개발 속도와 팀 숙련도 | 기존 화면의 토큰 수정과 로컬 단일 페이지 빌드 | 같은 출발점에서 필요한 UI를 만드는 시간, 팀의 작성 경험, CI 빌드 시간. 토큰 수정 실험에서는 공통 Fast Refresh 경계 때문에 네 후보 모두 새로고침이 발생했습니다. |
| 브랜드 범위와 스타일 격리 | 계정에 따른 색상·글꼴·배경 전환, 후보별 독립 HTML, 브랜드 영역 안에 마운트한 모달 | 같은 문서의 여러 브랜드와 기존 앱이 공존하는 경우, 포털 대상의 DOM 위치와 CSS 변수 상속, 전역 리셋·전역 스타일 충돌 |
| SSR·운영 배포 | Vite의 클라이언트 렌더링과 로컬 프로덕션 빌드 | 서버가 첫 HTML에서 브랜드를 결정하는 경로, 로그인 전후 기본 테마 깜박임, 서버/클라이언트 일치, 캐시와 실서비스 CSP 정책 |
| 브라우저·접근성 | Chrome의 390px 화면, 키보드로 모달 닫기와 포커스 복귀, 기본 색상·글꼴 | 지원 대상 Safari·Firefox·WebView, 브랜드별 실제 웹폰트 로딩, 색 대비, 키보드 흐름, 모션 감소 설정 |
| 운영 성능과 의존성 | 초기 gzip 자산, 브라우저의 CSS 규칙 수와 색상 정착 시간 | 실기기 첫 화면과 입력 반응, 실제 설치·갱신의 영향, 적용할 버전의 지원과 전이 의존성 변경 |

기존 Tailwind가 표준인 제품에는 **Tailwind + 같은 CSS 변수 계약**, 필요한 컴포넌트 재사용이 큰 화면에는 **shadcn/ui를 컴포넌트 단위로 추가**하는 선택이 합리적입니다. 기존 styled-components 화면은 현재 방식을 유지하면서 값 위주의 테마에 CSS 변수를 연결하는 선택지가 있습니다. 이 플레이그라운드의 새 화면 기본은 제품 조건이 바뀔 때 다시 검토합니다.

## 초기 구현 당시 시간 기록

아래 시간은 이번 세션에서 관측한 후보 작업 구간으로 코드 작성, 도구 응답 대기, 첫 검증을 포함합니다. 공통 대시보드를 먼저 작성했고, 이후 후보가 앞의 작업을 재사용했습니다. 각 후보의 독립 구현 시간이나 사람의 순작업 시간을 추정할 근거로 사용하기 어렵습니다. 첫 렌더와 전체 동작 통과 사이의 시간, 재작업과 대기의 세부 구간은 계측하지 못했습니다.

| 후보 | 관측된 경과 | 이 구간에서 한 작업 |
|---|---:|---|
| CSS Modules + React Context | 2분 55초 | 공통 대시보드, 브랜드 정책, CSS Modules 스타일과 최초 브라우저 시나리오 |
| styled-components | 51초 이내 | 기존 스타일을 런타임 테마로 옮기고 브라우저 시나리오 통과. 다음 후보로 넘어간 시점까지가 관측 상한 |
| Tailwind CSS | 1분 22초 | 공통 마크업에 적용할 유틸리티와 브랜드 변수 연결 작성 및 첫 브라우저 검증 |
| shadcn/ui | 28초 | 이미 받은 레지스트리 컴포넌트 3개를 공통 화면에 연결하고 첫 빌드·브라우저 검증. 앞서 병행한 레지스트리 설치 시간은 구간에서 제외 |

공통 초기 설정, 후보별 동작 확인 이후의 리뷰와 보정, 전체 검증은 위 표에 포함하지 않았습니다. 이번 순서에서는 shadcn이 Tailwind 구현을 그대로 활용했으므로 구간 차이에는 재사용 효과가 포함됩니다.

## 동일한 테마 변경의 속도와 복잡도

초기 구현 순서에 따른 재사용 효과를 보완하기 위해, 토큰을 분리한 구조에서 **브랜드별 상세 모달 테두리 토큰**을 추가하는 변경을 다시 측정했습니다. 후보마다 기존 회색 테두리를 확인한 뒤 임시 복사본에 준비된 패치를 적용했습니다. Vite 재시작과 Chrome 검증을 포함해 최초 Grove 적용 시점, Grove·Signal·Ember와 로그아웃까지 전체 검증한 시점을 따로 잽니다. 후보별 3회 측정의 중앙값과 범위입니다.

| 후보 | 패치 적용 중앙값 | 최초 적용 확인 | 전체 검증 | 후보별 수정 파일 / 지점 | 이 변경의 적용 경로 |
|---|---:|---:|---:|---:|---|
| CSS Modules + React Context | 5ms | 612ms (592–714) | 911ms (858–939) | 1 / 1 | 공통 CSS 변수 → 모듈의 모달 테두리 |
| styled-components | 5ms | 611ms (563–654) | 875ms (804–919) | 1 / 1 | Provider의 최종 테마 → 모달 스타일 보간 |
| Tailwind CSS | 10ms | 658ms (626–702) | 908ms (853–936) | 2 / 2 | 공통 CSS 변수 → Tailwind 색상 매핑 → 모달 클래스 |
| shadcn/ui | 11ms | 724ms (706–761) | 953ms (935–1019) | 2 / 2, shadcn 전용 0 / 0 | 공유 Tailwind 매핑과 모달 클래스를 그대로 사용 |

공통 준비에는 기본값, 허용 키와 브랜드별 색상 3개, CSS 변수 출력 등 **3개 파일의 6개 지점**이 쓰였고 후보별 시간과 변경량에서 제외했습니다. shadcn의 파일 2개는 단독 재현에 포함된 Tailwind 파일이며, 두 후보를 같이 유지하는 작업량은 **총 2개 공유 파일**입니다. 이 실험의 모달은 공통 React 컴포넌트이므로 shadcn 레지스트리 컴포넌트 수정 비용은 여기서 계측하지 않았습니다.

시간은 준비된 패치의 적용부터 시작합니다. 사람이 처음 설계하고 편집하는 시간은 초기 구현 기록을 참고하며, 초기 도입 속도의 우열은 보류합니다. 재실행 시간은 브라우저와 Vite에 영향을 받으므로 표의 수십 ms 차이에 일반적인 구현 속도 순위를 부여하지 않습니다. 원시 기록의 각 행에서 세 구간을 확인할 수 있습니다. [12회 측정 원본](evidence/brand-outline-benchmark.json)

같은 변경을 재실행하는 명령과 원본은 [실험 지침](README.md#재실행과-원본)에 있습니다.

## 브라우저와 빌드

`npm run build` 후 `npm run measure`로 로컬 프로덕션 빌드를 열었습니다. 후보별 1280×900의 새 Chrome 컨텍스트에서 Grove와 Signal을 번갈아 선택했습니다. 워밍업 2회 이후 20회를 기록했습니다. JS·CSS 크기는 각 HTML의 프로덕션 매니페스트에서 따라갈 수 있는 초기 자산을 중복 제거한 뒤 gzip으로 합산했습니다.

| 후보 | JS gzip (바이트) | CSS gzip (바이트) | 계정 상태 반영 p50 / p95 | 글꼴·버튼·페이지 배경 적용 p50 / p95 |
|---|---:|---:|---:|---:|
| CSS Modules + React Context | 74,559 | 2,226 | 16.6 / 16.8 ms | 16.7 / 16.8 ms |
| styled-components | 86,723 | 237 | 16.6 / 16.7 ms | 16.6 / 16.7 ms |
| Tailwind CSS | 75,854 | 4,745 | 16.6 / 16.7 ms | 16.6 / 16.7 ms |
| shadcn/ui | 89,015 | 5,815 | 16.7 / 16.9 ms | 166.8 / 167.0 ms |

계정 상태는 다음 프레임 콜백에서 DOM의 브랜드 값으로 확인했습니다. 스타일은 제목 글꼴, 첫 행 버튼 배경색, 페이지 배경색의 계산값이 새 브랜드 값에 도달할 때까지 프레임마다 확인했습니다. 토큰 분리 후 측정부터 페이지 배경 조건을 추가했습니다. 이 측정에는 프레임 대기 시간이 포함되며 실제 화면 표시 시점은 계측하지 않았습니다. shadcn 버튼의 기본 `transition-all`은 브라우저에서 150ms로 확인됐습니다. 이 애니메이션이 버튼 색상 정착 시간에 반영됐습니다.

Chrome 자동 테스트 18개에서 공통 토큰과 브랜드 오버라이드 검증에 더해 네 구현의 초기 env, 계정 전환, 재로드, 로그아웃, 모달과 키보드 포커스, 390px 화면에서의 테이블 스크롤을 확인했습니다. 지정된 `callu9ine` Chrome 프로필로 최종 빌드를 열어 네 후보에서 Signal·Ember의 지정 배경, Grove의 공통 배경, 카드 테두리와 모서리 값을 확인했습니다. 고정 데이터와 데모 계정으로 검증했으며 운영 로그인과 운영 배포는 검증 범위 밖입니다.
