# 04. 작업 상태 조회와 취소

[실험 목차](../README.md) · [실험 지침](README.md) · [Playground](http://127.0.0.1:5173/experiments/job-status/#playground) · [측정 원본](evidence/)

[비교 조건](#무엇을-비교했나) · [측정 결과](#측정-결과) · [폴링으로 충분한 조건과 전환 기준](#폴링으로-충분한-조건과-전환-기준) · [해석 한계](#해석-한계와-미측정)

장시간 분석 작업의 상태(대기 → 진행 → 완료)를 폴링으로 보여 줄 때, 서버의 요청 제한과 사용자의 취소, 같은 작업을 여러 탭에서 여는 상황까지 더해 **폴링이 어디까지 충분하고 언제 SSE로 바꿔야 하는지** 비교했습니다. 이전 [작업 상태 실험](https://github.com/callu9/personal-playground-react-ts/blob/60c12c6/docs/experiments/dashboard-refresh/results.md)을 별도 실험으로 복원하고 조건을 더한 것입니다.

**이 로컬 모의 조건에서 폴링은 "완료·취소 표시가 3초 안팎 늦어도 되고, 탭 수 ÷ 조회 간격이 서버 한도 안에 드는" 화면까지 충분했습니다.** 취소를 누른 뒤 `Cancelled`가 보이기까지 중앙값은 SSE 862 ms, 적응형 1,274 ms, 고정 1초 1,431 ms, 고정 3초 2,522 ms, 고정 5초 2,902 ms였습니다. 같은 작업을 5개 탭에서 3초 폴링으로 보면 요청 31건 중 10건이 `429`였고 완료 반영 p95가 6,297 ms로 늘었습니다. 취소를 1초 안에 보여 주거나 탭이 한도를 넘거나 중간 상태를 놓치면 안 된다면 SSE로 바꿀 근거가 생깁니다. 다만 SSE도 같은 프로필의 탭 20개에서는 동시 연결이 6개에서 멈춰 탭 14개가 중간 상태를 하나도 보지 못했습니다. [조건별 선택](#폴링으로-충분한-조건과-전환-기준)

## 무엇을 비교했나

| 축 | 값 |
|---|---|
| 조회 방식 | 고정 폴링 1·3·5초, 적응형 폴링(대기 4초 · 진행·취소 중 1초), SSE |
| 429 처리(폴링) | **Retry-After 준수**(헤더의 초, 원래 간격보다 짧지 않게, 0~250 ms 지터) · **백오프만**(0.5~8초 두 배 백오프, 헤더 무시). SSE는 `EventSource`가 상태 코드와 헤더를 주지 않아 백오프만 가능 |
| 서버 조건 | 정상(전달 지연 40 ms) · 느린 응답(1,350 ms) · 일시 단절(시작 후 5.8~8.5초) · 요청 제한(같은 작업의 조회 8건/10초, 초과 시 `429` + `Retry-After`) |
| 취소 | 작업 시작 후 6.5초에 **Cancel job**. 서버는 즉시 `Cancelling`, 800 ms 뒤 `Cancelled`를 보고 |
| 탭 | 같은 작업을 1·5·20개 탭에서 조회. 한 브라우저 프로필에서 열었고, SSE 20개는 탭별 프로필 대조도 측정 |

작업은 생성 2초 뒤 시작하고 시작 기준 4.52·5.35·6.18·7.83·9.89·12.20초에 버전 1~6을 기록합니다. 요청 제한은 같은 작업을 보는 모든 탭이 공유하며, 운영에서 사용자·IP·API 키 단위로 걸리는 한도의 대역입니다. 거절한 요청은 한도에 세지 않고 `Retry-After`는 가장 오래된 요청이 창에서 빠질 때까지 남은 초(올림, 최소 1초)입니다. [실험 지침](README.md#비교-설계)

## 구현과 검증 비용

이전 작업 상태 실험의 계약·스케줄러·모의 서버를 복원하고 취소, 요청 제한, 429 처리, SSE 재연결을 더했습니다. 새 패키지 의존성은 없습니다.

| 후보 | 후보별 코드(비공백 줄) | 이번에 더한 부분 | 변경할 때 확인할 점 |
|---|---|---|---|
| 고정 폴링 | `polling.ts` 55줄(공통 스케줄러) | 429 분기와 `Retry-After` 파싱 약 13줄, 취소·완료에서 중단 | 지원 주기는 `contract.ts` 한 곳. 단일 요청·6초 제한·백오프는 공통 스케줄러 |
| 적응형 폴링 | `adaptive.ts` 6줄 | 진행뿐 아니라 취소 중에도 1초 | 대기 → 진행 전환은 대기 주기만큼 늦게 감지 |
| SSE | `sse.ts` 35줄 + 서버 스트림 | 닫힌 연결을 백오프로 다시 열기, 취소·단절 때 마지막 버전부터 이어받기 | `429`·`404`는 `EventSource`를 닫고 사유를 알려 주지 않음. 프록시 버퍼링, 탭당 연결, 브라우저 연결 한도 |

모의 서버 `server.ts`는 229줄(복원 전 이전 서버 182줄)입니다. 구현에 든 시간은 이 작업에서 후보별로 재지 않았습니다(미측정).

## 측정 방법

- **환경.** macOS(Darwin 27.2.0) arm64 · Apple M2 · 8코어 · 24 GiB · Node v24.18.0 · Chrome 158.0.8127.37 · 1280×900 · Playwright 헤드리스(`channel: 'chrome'`), 새 브라우저 컨텍스트. 프로덕션 빌드를 로컬 Vite 미리보기(HTTP/1.1)로 서비스합니다. 이전 작업 상태·대시보드 실험은 Windows(i5-14400F)에서 측정했으므로 이 보고서의 표에는 섞지 않았습니다.
- **반복.** 정상·요청 제한은 후보별 3회, 느림·단절은 후보별 2회, 취소는 후보별 5회, 여러 탭은 조합별 1회(SSE 20탭 공유·별도 프로필, 요청 제한 5·20탭은 2회). 같은 회차의 후보는 병렬로 실행하고 회차마다 순서를 돌렸으며, 정상·요청 제한은 탭 시작 오프셋 0·1.1·2.35초, 취소는 0·0.6·1.2·1.8·2.4초를 썼습니다.
- **반영 지연**은 서버 기록 시각 → Chrome DOM에 해당 버전 행이 나타난 시각이며, p95는 관측한 버전만 모읍니다. 미관측 버전은 따로 셉니다. 표본이 작아 p95는 최댓값과 같은 경우가 많습니다.
- **취소 반영 시간**은 Cancel job 클릭 시각 → `Cancelled` 행의 DOM 등장 시각입니다. 요청 탭과 관찰만 하는 다른 탭을 따로 봅니다. 서버 확정까지의 하한은 요청 지연 40 ms + 800 ms입니다.
- **요청량**은 상태 조회(429·503 포함)와 SSE 연결·재연결 합계입니다. 탭당 분당 값은 작업 생성부터 통계 조회 시각까지(정상 약 19.5초, 요청 제한 다탭은 완료를 기다려 최대 45초)로 환산합니다. 헤더·TLS는 제외합니다. `Retry-After 전 재요청`은 서버가 본 요청 중 직전 429의 대기 시간 안에 도착한 수로, 탭을 구분하지 못해 단일 탭에서만 해석합니다.
- 모든 표본에서 탭이 숨김 상태가 된 적이 없는지 검사했습니다. 작업 시나리오와 서버 한도는 합성이며 운영 값이 아닙니다.

5개 탭의 3초 폴링은 한도(0.8건/초)보다 많은 약 1.7건/초를 요구해 작업당 10건이 거절됐고 완료 p95가 정상(954 ms)의 6.6배로 늘었습니다. 백오프만 쓴 폴링은 요청을 56건으로 늘리고도 더 늦었습니다(9,982 ms). 20개 탭에서는 Retry-After를 지킨 쪽이 40/40 탭에 완료를 보였지만 p95가 27 s였고, 백오프만 쓴 쪽은 p95 17.9 s였으나 40개 중 8개 탭이 45초 안에 완료를 보지 못했습니다. 같은 시각에 재시도하는 탭이 한 번에 열린 칸만 통과하기 때문이라고 추정하지만(가설) 탭별 재시도 시각은 기록하지 않았습니다. SSE 20탭은 연결 시도 20건이 한도를 넘어 30건이 거절됐고 연결은 6개까지만 열렸지만 40/40 탭이 완료를 보았습니다. 이 표의 `Retry-After 전 재요청`은 탭을 구분할 수 없어 싣지 않았습니다.

## 폴링으로 충분한 조건과 전환 기준

허용 지연과 요청 예산을 먼저 정하고 그 두 조건을 만족하는 가장 긴 간격을 고릅니다. 한 사용자의 요청 한도가 *R*건/*W*초이면 폴링은 **탭 수 ÷ 조회 간격(초) ≤ R ÷ W**를 지켜야 합니다. 8건/10초에서는 간격 1초 0.8개, 3초 2.4개, 5초 4개 탭까지입니다. 이 값을 넘긴 5탭 3초 측정에서 거절이 늘고 완료가 늦어졌습니다.

| 화면의 조건 | 선택 | 이 실험의 근거 |
|---|---|---|
| 완료·취소 표시가 3초 안팎 늦어도 되고, 한 작업을 한두 탭에서 보며 한도에 여유가 있다 | **고정 3초**(요청을 더 줄이려면 5초) | 취소 반영 중앙값 2,522 ms(5초 2,902 ms), 작업당 5.7건, 429 없음 |
| 취소·완료를 1.5초 안팎에 보여 주고 탭이 한 개다 | **적응형** 또는 **고정 1초**, 둘 다 `Retry-After` 준수 | 취소 1,274~1,431 ms, 한도 8건/10초에서 1초 폴링은 작업 막바지에 약 1건 거절 |
| 한 작업을 여러 탭(5개 이상)에서 열거나 한도가 탭 수 ÷ 간격에 못 미친다 | **SSE**나 탭 사이에 연결을 공유하는 방식(후자는 미측정) | 5탭 3초 폴링 429 10/31건, 완료 p95 6.3 s. 같은 5탭 SSE는 429 0건, 완료 p95 70 ms |
| 취소를 1초 안에 반영해야 한다 | **SSE** | 중앙값 862 ms(서버 하한 840 ms), 폴링 중 가장 빠른 고정 1초는 1,431 ms |
| 중간 상태를 하나도 놓치면 안 된다 | **SSE**의 재생이나 증분 조회 | 정상 전달에서 SSE 미관측 0/18, 고정 3초 8/18 |

SSE로 바꾸면 해야 할 일도 측정으로 확인했습니다. (1) 같은 프로필의 탭이 6개를 넘으면 HTTP/1.1에서는 연결이 6개에서 멈추므로 HTTP/2나 탭 간 연결 공유가 필요합니다(HTTP/2는 미측정). (2) `EventSource`는 `429`의 `Retry-After`를 읽을 수 없어 재연결 간격을 짐작해야 합니다. 응답 헤더가 필요하면 `fetch` 스트림이 필요합니다(미측정). (3) 연결을 오래 두는 서버·프록시의 버퍼링과 타임아웃은 이 로컬 서버에서 보이지 않습니다.

탭이 하나이고 표시 지연이 3초면 충분한 화면에서는 폴링을 먼저 두고, 위 표의 조건이 하나라도 요구사항이 될 때 SSE를 검토하는 순서가 이 측정과 맞습니다. 실제 허용 지연·요청 예산·탭 수 분포는 이 실험이 정하지 못합니다.

## 해석 한계와 미측정

- 모의 서버, 한 대의 Mac, 프로덕션 빌드의 로컬 미리보기입니다. 원본 프로젝트 재현이나 운영 관측이 아닙니다.
- 표본이 작습니다. 취소는 후보별 5회, 여러 탭은 조합별 1~2회입니다. 다탭 p95는 대부분 최댓값이며, 20탭 요청 제한 결과는 재현성을 확인하지 못했습니다.
- 한도의 키를 작업 하나로 둔 것은 한 사용자의 한 작업을 가정한 것입니다. 실제 서비스에서는 같은 사용자의 다른 요청이 한도를 나눠 씁니다.
- Retry-After 지터는 0~250 ms로 짧습니다. 더 넓은 지터나 탭 간 조율은 측정하지 않았습니다.
- 미측정: 취소 응답 직후 즉시 다시 조회하기, ETag·304, HTTP/2, `fetch` 스트림, SharedWorker·BroadcastChannel을 이용한 탭 간 공유, 서버 CPU·연결 처리량, 인증 만료, 작업 수십 개를 한 화면에서 보는 목록, 실제 브라우저의 백그라운드 탭 타이머 제한.
- 구현 시간은 후보별로 재지 않았습니다.
