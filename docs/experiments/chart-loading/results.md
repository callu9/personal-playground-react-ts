# 06. 차트 지연 로딩

[실험 목차](../README.md) · [실험 지침](README.md) · [Playground](http://127.0.0.1:5173/experiments/chart-loading/#playground) · [측정 원본](evidence/)

[비교 조건](#무엇을-비교했나) · [측정 결과](#측정-결과) · [무엇을 고르나](#무엇을-고르나) · [해석 한계](#해석-한계와-미측정)

차트가 열두 개인 화면에서 차트 모듈을 **언제 불러오고 언제 그리는지**에 따라 LCP, 첫 입력, 스크롤 중 입력 반응, JS 힙이 어떻게 달라지는지 비교했습니다. 전략은 Eager(정적 import, 모두 즉시), Split(별도 청크, 모두 즉시), Viewport(별도 청크, 보일 때), Viewport + idle preload(보일 때 그리되 청크는 한가할 때 미리 받음)입니다. 차트는 `chart.js/auto`이고 첫 화면에는 제목·지표 카드·서비스 표만 있어 **차트가 화면 아래에서 시작합니다.**

**차트 모듈을 별도 청크로 나누는 것만으로 이 화면의 첫 입력 처리 시작은 절반 가까이, LCP는 4분의 1쯤 빨라졌고, "보일 때 그리기"는 로드 직후의 롱태스크와 JS 힙을 없앴습니다.** CPU 4배 감속·10 Mbps·왕복 60 ms에서 Eager는 LCP 404 ms, 첫 입력 처리 시작 694 ms, 차단 시간 260 ms, 로드 3초 뒤 JS 힙 6.8 MB였고, Viewport는 304 ms, 341 ms, 0 ms, 1.9 MB였습니다. 대신 스크롤로 첫 차트가 화면에 들어온 뒤 그려지기까지 202 ms 동안 빈 카드가 보였고, 청크를 한가할 때 미리 받아 두면(idle preload) 이 시간이 99.5 ms로 줄었습니다. 스크롤 중 INP는 네 전략 모두 24~32 ms로 차이가 없었습니다. ## 무엇을 비교했나

| 전략 | 불러오기 | 그리기 |
|---|---|---|
| Eager | 차트 모듈을 첫 번들에 정적 import | 마운트 직후 열두 개 모두 |
| Split | 별도 청크(`import()`), 마운트 직후 요청 | 청크 도착 직후 열두 개 모두 |
| Viewport | 별도 청크, 카드가 뷰포트 200px 안에 들어올 때 처음 요청 | 그 카드부터 |
| Viewport + idle preload | Viewport와 같되 `load` 뒤 `requestIdleCallback`(최대 2초)으로 청크를 미리 받음 | 뷰포트에 들어올 때 |

전략마다 별도 HTML 진입점을 두어 번들 구성이 다르며 페이지·데이터·스타일·차트 설정은 공유합니다. 새 의존성은 `chart.js` 하나입니다. [실험 지침](README.md#비교-설계)

## 구현과 검증 비용

| 전략 | 전략별 코드 | 변경할 때 확인할 점 |
|---|---|---|
| Eager | 정적 import 한 줄 | 차트 모듈 크기가 첫 번들에 그대로 더해집니다. |
| Split | 동적 `import()` 한 줄과 도착 뒤 그리기 | 청크 요청이 첫 번들 실행 뒤에 시작되어 한 단계 늦습니다. 로딩 실패 처리가 필요합니다. |
| Viewport | `IntersectionObserver`(카드당 한 개)와 `rootMargin` | 여백이 작으면 빈 카드가 보이고 크면 미리 그리는 양이 늘어납니다. 관찰 해제와 정리를 직접 관리합니다. |
| Viewport + idle preload | 위에 `requestIdleCallback`으로 `import()` 호출 한 번 | 한가할 때 네트워크와 파싱을 씁니다. `requestIdleCallback`이 없는 브라우저는 `setTimeout`으로 대체했습니다. |

구현 시간은 후보별로 재지 않았습니다(미측정).

## 측정 방법

- **환경.** macOS(Darwin 27.2.0) arm64 · Apple M2 · 8코어 · 24 GiB · Node v24.18.0 · Chrome 158.0.8127.37 · Chart.js 4.6.2 · React 19.3.1 · 1280×900 · Playwright 헤드리스(`channel: 'chrome'`)·새 브라우저 컨텍스트. 프로덕션 빌드를 로컬 Vite 미리보기(HTTP/1.1, 압축 없음)로 서비스합니다. 다른 기기의 수치와 섞지 않았습니다.
- **조건.** `throttled`: CPU 4배 감속 + 10 Mbps·왕복 60 ms. 전략별 5회. `plain`: 감속 없음, 전략별 3회. 회차마다 전략 순서를 돌렸습니다. 표는 중앙값(최소–최대)입니다.
- **로드 종류.** LCP·차단 시간·JS 힙(로드 후)·로드 시점 차트는 **입력 없이** 로드한 페이지에서 로드 3초 뒤에 읽습니다(입력이 있으면 브라우저가 LCP 보고를 멈춥니다). 첫 입력·스크롤 INP·빈 카드·JS 힙(스크롤 후)은 별도 로드에서 Ping 버튼이 생기자마자 누르고 로드 3초 뒤 600px씩 8번 스크롤하며 단계마다 누른 값입니다.
- **지표 정의.** 차단 시간은 5초 안의 롱태스크마다 `max(0, 길이 − 50 ms)`의 합입니다. 첫 입력 처리 시작은 클릭 이벤트의 `processingStart`(탐색 시작 기준), 스크롤 중 INP는 스크롤 중 상호작용 8개 중 가장 긴 이벤트 `duration`(8 ms 단위)입니다. 첫 차트 빈 카드는 카드가 화면(여백 없음)에 처음 들어온 시각부터 그 차트가 그려진 시각까지이며 미리 그려졌으면 0입니다. JS 힙은 강제 GC 뒤 `JSHeapUsedSize`입니다.

- **LCP·첫 입력**: 차트 모듈을 첫 번들에서 빼면(Split부터) 첫 화면 JS가 140.49 kB에서 71.18 kB(gzip)로 줄었고 LCP가 404 → 약 300 ms, 첫 입력 처리 시작이 694 → 약 335 ms였습니다. Eager의 LCP 범위(360–660 ms)는 가장 넓었습니다. 감속이 없을 때도 방향은 같았습니다(LCP 124 → 52~56 ms, 첫 입력 140 → 72~132 ms).
- **차단 시간**: Eager는 열두 개를 그리는 롱태스크 하나가 260 ms였고, Split은 같은 롱태스크가 LCP 뒤로 밀려 54 ms로 집계됐습니다. Viewport 계열은 로드 직후 롱태스크가 없었습니다.
- **Split과 Viewport의 차이**: LCP와 첫 입력은 거의 같았습니다(304 대 304 ms, 332 대 341 ms). 차이는 로드 직후 차트 12개를 그리는 비용과 힙(6.9 대 1.9 MB)이었습니다. 스크롤 뒤에는 모든 전략이 7.9 MB로 같았습니다.
- **빈 카드**: Viewport는 첫 차트가 화면에 들어온 뒤 202 ms(200–223) 동안 비어 있었습니다. 이 시간에는 청크 요청·파싱과 첫 그리기가 들어 있고, idle preload는 청크를 미리 받아 99.5 ms(77–107)로 줄었습니다. 남은 시간은 첫 차트를 그리는 비용이라고 추정합니다(가설). 감속 없이는 48 대 36 ms였습니다.
- **스크롤 중 INP**: 네 전략 모두 24~32 ms(`throttled`)로, 8 ms 해상도 안에서 차이가 없었습니다. 스크롤 중 차트를 하나씩 그리는 비용이 클릭을 막지 않았습니다.

## 무엇을 고르나

| 상황 | 선택 | 이 실험의 근거 |
|---|---|---|
| 차트가 첫 화면 아래에 있고 열두 개쯤 된다 | **Viewport**(보일 때 그리기) | Eager 대비 LCP 404 → 304 ms, 차단 260 → 0 ms, 로드 후 힙 6.8 → 1.9 MB |
| 같은 조건에서 스크롤했을 때 빈 카드가 거슬린다 | **Viewport + idle preload** | 첫 차트 빈 카드 202 → 99.5 ms. 대가는 한가할 때 받는 청크 70.25 kB(gzip) |
| 구현을 가장 단순하게 두고 첫 화면과 입력만 개선하고 싶다 | **Split** | 번들 분리만으로 LCP·첫 입력이 Viewport와 같은 수준. 열두 개를 한꺼번에 그리는 롱태스크(54 ms)와 힙 6.8 MB는 남음 |
| 차트 몇 개가 첫 화면 안에 있다 | 이 실험으로는 판단 불가 | 모든 차트가 화면 아래인 구성만 측정했습니다(미측정) |
| 차트 수가 훨씬 많거나 한 차트가 더 무겁다 | 스크롤 INP를 다시 재야 함 | 이번 구성에서는 스크롤 INP에 차이가 없었지만 차트 수·크기를 바꾸지 않았습니다(미측정) |

## 해석 한계와 미측정

- 합성 데이터의 `chart.js/auto`(전체 등록) 열두 개입니다. 트리 셰이킹한 등록, 다른 차트 라이브러리, 서버 렌더링된 이미지 차트는 측정하지 않았습니다. 청크가 작아지면 로딩 전략의 효과도 줄어듭니다.
- 한 대의 Mac, 헤드리스 Chrome, CPU 4배 감속과 10 Mbps는 실제 기기·망이 아닙니다. 로컬 미리보기는 압축이 없어 전송량이 gzip 크기와 다릅니다. 모든 표본이 한 번의 실행에서 나왔습니다.
- 표본은 `throttled` 5회, `plain` 3회입니다. 스크롤 INP는 8 ms 단위라 차이가 없다는 결론은 그 해상도 안에서만 성립합니다.
- 측정을 마친 뒤 좁은 화면용 보정(서비스 표를 가로 스크롤 영역으로 감싸고 지표 카드를 2열로 줄임)을 했습니다. 1280px 화면의 레이아웃은 같지만 그 상태로 다시 재지는 않았습니다.
- 차트는 모두 첫 화면 아래에 있고 카드 높이가 고정되어 있어 레이아웃 이동(CLS)은 측정하지 않았습니다. 실사용 INP, 다른 탭 상태, 캐시된 재방문, HTTP/2는 미측정입니다.
