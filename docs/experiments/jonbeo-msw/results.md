# 03. Jonbeo MSW와 입력 반응성

**원본에서는 MSW 초기화를 기다리는 렌더링 게이트 때문에 첫 화면에서 입력할 수 없었다.** 플레이그라운드에서 보유 종목 UI를 먼저 그리니 첫 방문의 버튼 준비가 요청 통과에서 **201.5ms**, 모의 응답에서 **171.2ms** 빨라졌다. 데이터가 표시된 뒤 같은 동작의 INP는 아래 표에 기록했다. 추가 측정에서는 첫 방문 데이터 표시가 늦어진 방향이 반복되지 않았다. 원본 개발 서버의 통화 전환은 이벤트 처리 구간에서 가장 많은 시간을 썼다. [재측정과 Chrome trace](#데이터-표시-지연-재측정)

## 원본 코드에서 확인한 경로

1. 게이트 제거 직전 `d68ac41`에서 `MSWComponent`는 초기 상태의 `mswReady`가 `false`이면 하위 앱 전체를 렌더링하지 않았다. 개발 모드에서는 effect가 `initMocks()`를 호출하고 브라우저에서 `await worker.start()`가 끝날 때까지 이 상태가 지속된다. 등록이 실패하면 준비 상태를 갱신하는 경로도 없었다. [MSWComponent](https://github.com/callu9/jonbeo-next-ts/blob/d68ac41/src/providers/MSWComponent.tsx) · [초기화 코드](https://github.com/callu9/jonbeo-next-ts/blob/d68ac41/src/mocks/index.ts)
2. 해당 커밋의 포트폴리오 페이지는 서버 데이터 계층에서 보유 종목을 읽었다. 브라우저의 포트폴리오 mock은 별도 개발 주소에 150ms 지연을 설정했고, 화면에는 250ms를 기본값으로 하는 스켈레톤 유지 로직도 있었다. 화면이 비어 있던 시간, 스켈레톤을 표시한 시간, HTTP 응답 시간은 각각 따로 재야 한다. [페이지](https://github.com/callu9/jonbeo-next-ts/blob/d68ac41/src/app/page.tsx) · [데이터 접근](https://github.com/callu9/jonbeo-next-ts/blob/d68ac41/src/apis/portfolio.ts) · [mock 핸들러](https://github.com/callu9/jonbeo-next-ts/blob/d68ac41/src/mocks/handler/portfolio.ts) · [스켈레톤 훅](https://github.com/callu9/jonbeo-next-ts/blob/d68ac41/src/hooks/useMinLoading.tsx)
3. `76f9ac6`은 레이아웃의 `initMocks()` 호출과 Provider의 `MSWComponent` 경계를 제거했다. Jonbeo의 과거 보고서에는 이후 프로덕션 Lighthouse 기준선이 있지만, 당시 문제 입력의 FID·INP trace나 현장 표본은 저장소에서 확인되지 않았다. Lighthouse 점수는 과거 수치로만 참고했다. [게이트 제거 커밋](https://github.com/callu9/jonbeo-next-ts/commit/76f9ac6) · [Jonbeo 성능 보고서](https://github.com/callu9/jonbeo-next-ts/blob/main/docs/performance-refactoring.md)

두 커밋의 Next 개발 서버도 Chrome에서 실행했다. 등록 호출을 보류한 동안 `d68ac41`에서는 포트폴리오 제목이 보이지 않았고, 등록을 재개하자 제목과 종목을 표시했다. `76f9ac6`에서는 등록 호출 없이 등록을 보류한 상태에서도 동일한 제목과 종목을 표시했다. 이 검사는 원본 코드에서 대기의 영향만 확인했으며, 보류 시간을 성능 수치에 포함하지 않았다. [원본 실행 관측값](evidence/jonbeo-msw-history.json)

## 동일 조건 설계

| 경로 | 실제 처리 | 설정 지연 |
|---|---|---:|
| MSW 끔 | 제어 워커 없이 Vite 로컬 API 요청 | API 타이머 150ms |
| 요청 통과 | 실제 Service Worker에서 가로챈 뒤 `passthrough()`로 같은 API 요청 | 같은 API 타이머 150ms |
| 모의 응답 | 실제 Service Worker에서 가로챈 뒤 앱의 MSW 핸들러가 응답 | mock 핸들러 타이머 150ms |

- 원본과 같은 종목 수인 합성 포트폴리오 7개를 사용했다. 본문, HTTP 상태, `Content-Type`, 캐시 정책을 맞췄다. 출처 헤더와 Chrome의 `fromServiceWorker()`, controller 경로로 세 조건을 확인하고, 모든 본문의 SHA-256을 대조했다.
- **개선 전**은 준비가 끝나면 보유 종목 영역을 보여 준다. **개선 후**는 빈 목록 상태와 정렬 버튼을 즉시 마운트한다. 두 구현 모두 워커가 필요한 경로의 fetch는 준비 후에 시작한다. 원본은 앱 전체를 가렸고, 실험에서는 설정 UI를 공통으로 유지한 채 보유 종목 영역에만 같은 대기 의존성을 적용했다. [MSW 워커 시작 API](https://mswjs.io/api/setup-worker/start) · [요청 통과 API](https://mswjs.io/api/passthrough)
- API의 타이머는 Node에서 실행하고, mock 타이머는 워커가 메시지를 보낸 페이지의 MSW 핸들러에서 실행한다. 타이머 설정값을 맞춘 뒤 브라우저에서 실제 헤더 도착까지 잰다. 측정 차이에는 타이머 스케줄링, 스레드 간 메시지, HTTP 경로가 함께 포함된다.
- **입력 가능 시점**은 탐색 시작부터 보유 종목 영역과 정렬 버튼이 DOM에 커밋될 때까지다. 워커 모듈 로드를 일부러 멈춘 회귀 테스트에서는 개선 후 버튼을 눌러 상태가 변경되고 데이터를 받은 뒤에도 정렬이 유지됨을 확인했다.
- **INP**는 데이터 로딩 후 실제 Chrome 입력으로 정렬 버튼을 8회 누르고, 페이지를 벗어나 `visibilitychange`가 `hidden`이 된 뒤 `web-vitals/attribution`에서 수집한다. FID와 같은 구간인 첫 입력 대기는 `first-input`의 시작부터 처리 시작까지 따로 잰다. 시작 당시 입력이 불가능한 경우에는 버튼을 눌렀을 때의 INP 자체가 생기지 않는다. 로컬 INP는 이 입력 시나리오의 표본이며 실제 방문 p75는 측정 범위 밖이다. [Chrome INP 정의와 FID 차이](https://web.dev/articles/inp) · [web-vitals INP 및 attribution](https://github.com/GoogleChrome/web-vitals#inp)

## 데이터 표시 지연 재측정

초회 실행의 72.6ms와 145.2ms는 각 조건의 **데이터 DOM 커밋 시각 중앙값** 차이다. 개별 표본을 다시 나누면 두 경로 모두 요청을 보내기 전부터 차이가 있었다.

| 첫 방문의 초회 표본 | 탐색 → 워커 초기화 시작 | 탐색 → 요청 시작 | 요청 → 응답 본문 | 본문 → 데이터 DOM 커밋 |
|---|---:|---:|---:|---:|
| 요청 통과 | 358.4 → 441.2 | 473.1 → 553.4 | 210.1 → 219.2 | 6.3 → 9.3 |
| 모의 응답 | 269.6 → 455.7 | 437.3 → 581.8 | 217.1 → 212.5 | 8.3 → 7.2 |

단위는 ms이며 각 셀은 독립적으로 낸 중앙값이다. 중앙값끼리 더해 전체 시간 차이를 계산할 수 없다. 워커 초기화 자체의 중앙값은 요청 통과 133.7 → 123.6ms, 모의 응답 136.0 → 121.6ms였다. 모의 응답 개선 후 첫 방문 한 회에는 워커 초기화가 3,313ms 걸렸으며, 이 회차는 원래 중앙값에 포함했다.

### Chrome trace로 확인한 구간

별도 실행에서 첫 방문 trace를 경로·구현별 3개씩, 총 18개 수집했다. 아래는 워커 경로의 구간별 중앙값이다. trace 기록에는 자체 비용이 있어 위 재측정과 합치지 않았다.

| 첫 방문 Chrome trace (ms) | 요청 통과 | 모의 응답 |
|---|---:|---:|
| 첫 앱 DOM 커밋 → 요청 준비 effect 시작 | 161.7 → 220.6 | 143.5 → 169.7 |
| 워커 초기화 시작 → 동적 모듈 준비 | 100.7 → 90.3 | 252.1 → 76.8 |
| 동적 모듈 준비 → 워커 준비 | 65.8 → 62.6 | 51.1 → 57.3 |
| API 요청 → 응답 본문 | 256.8 → 227.3 | 262.1 → 225.3 |
| React 상태 갱신 직전 → 데이터 DOM 커밋 | 11.4 → 12.0 | 9.8 → 11.4 |

- **요청 전.** 세 번째 모의 응답 trace에서 개선 후 데이터 커밋은 45.0ms 늦었다. 요청은 61.0ms 늦게 시작했고 응답 본문은 요청 뒤 16.1ms 빨리 도착했다. 초기 앱 DOM 커밋과 effect 사이의 메인 트랙에는 스크립트 평가, 스타일 계산, 레이아웃과 페인트가 기록됐다. 워커 초기화 전 브라우저 작업으로 요청이 밀릴 수 있는 구조였다.
- **워커 초기화.** 첫 회차에는 느린 모듈 다운로드가 양쪽에 있었다. 게이트를 적용한 모의 응답의 MSW 청크 요청 → 헤더는 3,021.5ms였고, 먼저 그린 요청 통과에서는 2,065.7ms였다. 같은 trace에서 청크 준비 후 워커가 준비되기까지는 각각 89.3ms, 86.9ms였다. 워커 초기화의 긴 표본에서도 오래 걸린 구간을 모듈 로드와 등록·활성화로 분리할 수 있었다.
- **응답 뒤.** 상태 갱신에서 DOM 커밋까지 중앙값 차이는 추적한 두 워커 경로 모두 2ms 이내였다. 이 구간은 업데이트 대기와 React 작업을 합한 시간이다. Chrome 메인 트랙의 다음 `Paint`도 별도로 기록했으며, 이 이벤트는 테이블이 화면에 실제 표시된 시점의 대용으로 사용하지 않았다.
- **판정.** 초회에 기록한 72.6ms·145.2ms는 주로 요청 시작 시각이 늦었던 배치에서 나왔다. 재측정과 trace에선 시작 작업과 동적 청크 시간의 변동이 더 컸고, UI를 먼저 그리면 같은 크기로 데이터가 늦어진다는 패턴은 재현되지 않았다. 초회 실행에는 trace가 없어 그때 어떤 태스크나 청크가 늦었는지까지 특정할 수 없다. [Chrome trace 구간과 이벤트 근거](evidence/jonbeo-msw-trace-analysis.json)


### Jonbeo 원본 클론 재측정

원본 `d68ac41`과 `76f9ac6`을 그대로 체크아웃해 Next 15.5.2 개발 서버에서 각각 7회 실행했다. 각 서버의 홈 경로와 API를 사전에 열어 첫 컴파일을 제외했다. 방문마다 헤드리스 Chrome의 새 컨텍스트와 페이지 CPU 4배 감속을 적용하고, 첫 종목이 보인 뒤 통화 전환 버튼을 8회 눌렀다. 각 커밋에서 별도의 Chrome trace도 한 개씩 수집했다.

| 원본 측정 중앙값 (ms) | `d68ac41` 게이트 적용 | `76f9ac6` 게이트 제거 |
|---|---:|---:|
| 탐색 → 응답 시작 (TTFB) | 295.2 | 261.6 |
| 탐색 → 첫 콘텐츠 페인트 (FCP) | 7,332 | 1,612 |
| 탐색 → 포트폴리오 제목의 첫 DOM 등장 | 6,439.0 | 335.2 |
| 응답 시작 → 제목의 첫 DOM 등장 | 6,280.9 | 70.5 |
| 탐색 → 통화 버튼의 첫 DOM 등장 | 6,439.2 | 335.7 |
| 탐색 → 첫 종목의 첫 DOM 등장 | 6,439.7 | 335.7 |
| 통화 전환 INP | 416 | 744 |
| INP 입력 대기 / 이벤트 처리 / 다음 페인트 대기 | 3.2 / 314.2 / 62.8 | 7.8 / 701.0 / 20.4 |

표의 INP 세 구성요소는 각각 중앙값이다. INP 범위는 200~488ms였고 게이트 제거 후에는 224~1,016ms였다. 별도 trace 한 쌍의 INP는 424 → 408ms였다. 각 trace에서 클릭 처리가 가장 오래 걸린 이벤트는 319.7ms와 288.1ms였고, 그 안에서 React DOM 개발 빌드의 호출 구간이 각각 약 308ms와 284ms를 차지했다. 이 호출 구간에는 앱 이벤트 처리와 그에 따른 작업이 함께 포함된다.

- **원본의 초기 표시 지연.** 제거 전 7회 모두 워커의 모의 응답 활성화 메시지 뒤에 제목이 등장했다. 중앙값은 탐색 → 등록 호출 **5,459.3ms**, 등록 호출 → 모의 응답 활성화 **90.6ms**, 활성화 → 제목 **512.5ms**였다. 수집한 한 trace에서는 MSW 동적 청크의 요청 → 헤더 수신에 약 **7,977ms**, 그보다 먼저 시작한 Next `main-app.js`의 스크립트 평가에 약 **1,516ms**가 걸렸다. 개발 번들 로드·실행과 초기화 이후의 React 작업까지 화면을 가리는 것이 게이트의 영향이다. 등록 자체의 비용은 그중 일부다.
- **응답과 종목 데이터.** 두 원본 홈이 사용하는 서버의 `getPortfolioData()`와 API 핸들러가 읽는 fixture가 동일했다. 서버 API로 대조한 1,061바이트 본문 해시가 같았고, 두 조건의 측정 페이지에서 브라우저의 `/api/portfolio` 또는 `/portfolio` 요청은 총 0건이었다. 이 경로에서 브라우저 mock의 150ms 응답 타이머가 종목 표시를 지연시켰다는 근거는 없다.
- **원인 판정.** 원본에서 재현한 문제는 개발 모드 진입 시 게이트가 화면을 오래 가리는 현상이다. 통화 전환 지연은 작은 입력 대기보다 긴 이벤트 처리에서 크게 나타났고, 게이트 제거 후 INP 감소는 확인되지 않았다. 원본의 종목 시점은 DOM의 첫 등장이다. 이 값으로 스켈레톤 유지가 끝난 시점이나 방문자의 실제 FID를 판단할 수 없다. 프로덕션 원본의 성능도 별도 측정이 필요하다. [원본 반복 표본과 trace 추출값](evidence/jonbeo-source-benchmark.json)

## 적용 판단

- **개발·QA에서 MSW가 필요한 경우**에는 페이지 전체를 준비 상태에 묶지 않는다. 독립적인 UI는 먼저 보여 주고, 응답 출처가 중요한 요청만 워커를 기다리게 한다. 등록이 실패하면 영역에 오류를 표시하거나 테스트를 실패 처리한다. 모의 데이터가 필요한 상황에서 API로 조용히 우회하면 테스트가 잘못 통과할 수 있다.
- **서버 fixture나 Route Handler로 충분한 경우**에는 Jonbeo의 수정처럼 포트폴리오 데이터를 서버가 제공하도록 하는 편이 단순하다. 워커 등록을 기다리는 경로가 줄고 코드에서 개발용 mock과 실제 데이터를 구분하기 쉬워진다. 다른 팀과 독립적으로 API 오류·지연을 재현해야 한다면 브라우저 인터셉션의 이점이 크다. [Jonbeo 서버 데이터와 Route Handler](https://github.com/callu9/jonbeo-next-ts/blob/main/docs/performance-refactoring.md)
- **표시된 버튼을 누르고도 느린 경우**에는 입력과 겹친 긴 메인 스레드 작업, 이벤트 처리, 다음 페인트를 각각 본다. 원본의 스켈레톤 최소 시간은 콘텐츠 표시를 늦추는 별도 후보이고, CPU 작업의 영향은 해당 작업과 입력 시점이 겹친 trace에서 판단한다.

## 재실행

```sh
npm ci
npm run build
npm run measure:msw
npx playwright test tests/jonbeo-msw.spec.ts --workers=1
```

`npm run dev`의 런처에서 **Jonbeo MSW performance**를 열면 세 요청 경로와 두 렌더링 방식을 바꿔 볼 수 있다. 워커는 실험의 `worker/` 하위에서만 등록되며 MSW 끔 경로와 다른 실험을 제어하지 않는다. 벤치마크는 원시 Event Timing과 Long Tasks, 응답 출처, 환경을 `test-results/jonbeo-msw/results.json`에 남긴다. 달리 지정하려면 `MSW_BENCH_ROUNDS`를 설정한다.

### Chrome trace 수집

프로덕션 빌드 뒤 PowerShell에서 실행한다. 환경 변수 없이 실행하면 계측 마크가 있는 일반 측정이고, trace 옵션은 첫 방문마다 Chrome CDP 기록을 추가한다. 브라우저 타이밍과 trace 타이밍은 별도 실행으로 비교한다.

```powershell
$env:MSW_BENCH_ROUNDS = '3'
$env:MSW_BENCH_TRACE = '1'
npm run measure:msw
Remove-Item Env:MSW_BENCH_TRACE, Env:MSW_BENCH_ROUNDS
```

`test-results/jonbeo-msw/traces/`의 `.json.gz`를 Chrome DevTools **Performance → Load profile**로 열고 **Timings**, **Main**, **Network**를 함께 본다. `jonbeo:appCommit`, `jonbeo:effect`, `jonbeo:workerStart`, `jonbeo:workerModuleReady`, `jonbeo:workerReady`, `jonbeo:request`, `jonbeo:body`, `jonbeo:stateUpdate`, `jonbeo:data` 순서로 확인할 수 있다. `jonbeo:data`는 레이아웃 effect에서 찍은 DOM 커밋 시점이다. [Chrome trace 사용법](https://developer.chrome.com/docs/devtools/performance/reference/) · [React useLayoutEffect](https://react.dev/reference/react/useLayoutEffect)
