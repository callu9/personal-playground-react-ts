# 05. 전역 상태 구독과 입력 반응

[실험 목차](../README.md) · [실험 지침](README.md) · [Playground](http://127.0.0.1:5173/experiments/state-subscription/#playground) · [측정 원본](evidence/)

[비교 조건](#무엇을-비교했나) · [측정 결과](#측정-결과) · [무엇을 고르나](#무엇을-고르나) · [원본 Jonbeo와의 관계](#원본-jonbeo와의-관계) · [해석 한계](#해석-한계와-미측정)

[Jonbeo MSW 실험](../jonbeo-msw/results.md)에서 통화 전환 INP의 가장 큰 구간은 이벤트 처리였습니다. 같은 모양의 화면(종목 행, 금액 포맷, 단위 전환 버튼)을 만들어 **상태 구독 방식과 구독 위치가 입력 반응을 얼마나 바꾸는지** 비교했습니다. 구독 방식은 Context 하나, Context 분리, Zustand 전체 구독, Zustand selector 구독이고, 구독 위치는 행 전체와 금액 셀·버튼입니다.

**이 합성 화면에서 단위 전환처럼 모든 행이 바뀌는 상호작용의 INP는 구독 방식으로 줄지 않았습니다. 줄어든 것은 구독 위치(행 전체 → 금액 셀)와 행 수였습니다.** 행 1,000개, CPU 4배 감속에서 행이 구독하면 네 방식 모두 단위 전환 INP가 192~208 ms였고, 금액 셀과 버튼만 구독하면 144~160 ms였습니다. 일부 행만 바뀌는 행 선택에서는 Zustand selector만 112~120 ms를 64 ms로 줄였습니다. 행 수는 가장 큰 변수여서 단위 전환 INP가 7행 48 ms, 100행 72 ms, 1,000행 200 ms 안팎이었습니다. [무엇을 고르나](#무엇을-고르나)

## 무엇을 비교했나

| 축 | 값 |
|---|---|
| 구독 방식 | Context · one(상태 전체를 값 하나에) · Context · split(단위·선택·액션을 세 Context로) · Zustand · whole store(`useStore()`를 선택자 없이 호출) · Zustand · selector(`useStore((state) => …)`) |
| 구독 위치 | row: 행이 구독하고 이름·차트·금액·버튼을 모두 다시 렌더링 · leaf: 행은 `memo`로 고정하고 금액 셀과 선택 버튼만 구독 |
| 행 수 | 7 · 100 · 1,000 (가상화 없음) |
| 상호작용 | 단위 전환(모든 행의 금액이 바뀜) · 행 선택(한 번에 한 행만 바뀜) |
| CPU | 4배 감속(Jonbeo 측정과 같은 조건), 행 1,000개는 감속 없음도 측정 |

네 방식은 같은 훅 인터페이스 뒤에 두었고 마크업·스타일·데이터·포맷터는 같습니다. 원본 스토어에는 단위(`isWon`) 하나뿐이어서 구독 범위의 차이가 드러나지 않으므로 **선택 상태를 이 실험이 더했습니다.** [실험 지침](README.md#비교-설계)

## 구현과 검증 비용

| 후보 | 후보별 코드(비공백 줄) | 구독 위치에 따른 차이 |
|---|---:|---|
| Context · one | 16줄 | 값 객체가 바뀔 때마다 그 Context를 읽는 모든 컴포넌트가 다시 렌더링됩니다. 액션만 읽는 버튼도 포함됩니다. |
| Context · split | 19줄 | 단위·선택·액션이 서로를 렌더링시키지 않습니다. 같은 상태를 읽는 행 사이에서는 하나만 고를 수 없습니다. |
| Zustand · whole store | 7줄 + 공통 스토어 6줄 | 의존성 `zustand` 하나가 늘었습니다. 선택자 없이 부르면 Context 하나와 같은 범위가 렌더링됩니다. |
| Zustand · selector | 7줄 + 공통 스토어 6줄 | 선택된 행 여부를 `state.selectedId === id`로 구독해 행 하나 단위로 좁힙니다. |

줄 수는 `bindings.tsx`에서 각 후보의 Provider와 훅 정의만 센 비공백 줄이며, Zustand 두 후보는 스토어 정의 6줄을 공유합니다. 구현 시간은 후보별로 재지 않았습니다(미측정).

## 측정 방법

- **환경.** macOS(Darwin 27.2.0) arm64 · Apple M2 · 8코어 · 24 GiB · Node v24.18.0 · Chrome 158.0.8127.37 · React 19.3.1 · Zustand 5.1.0 · Vite 8.3.8 · web-vitals 6.2.3 · 1280×900 · Playwright 헤드리스(`channel: 'chrome'`). 이전 Windows 측정값은 이 표에 섞지 않았습니다.
- **INP.** 일반 프로덕션 빌드를 로컬 미리보기로 서비스하고, 조건마다 새 브라우저 컨텍스트에서 5번 로드합니다. 로드마다 CDP 입력으로 8번 누르고(단위 전환 8번, 또는 서로 다른 행을 고르는 선택 8번, 클릭 사이 500 ms) `web-vitals/attribution`(`reportAllChanges`, 16 ms 임계)의 INP를 읽습니다. 표는 5회 로드의 중앙값과 최소–최대입니다. INP는 8 ms 단위로 보고되므로 8~16 ms 차이는 해상도 안입니다.
- **렌더링 횟수와 커밋.** `react-dom/client`를 `react-dom/profiling`으로 바꾼 프로덕션 빌드에서 조건당 2번 로드, 로드마다 8번 누른 16개 상호작용의 중앙값입니다. 컴포넌트 본문에서 센 렌더 횟수와 Profiler의 `actualDuration`(렌더 단계)이며, 상호작용마다 커밋은 1번이었습니다.
- 모든 조건은 탭이 숨겨지지 않았음을 검사했습니다. 원본 Jonbeo의 프로덕션 측정은 포함하지 않았습니다.

## 무엇을 고르나

| 상황 | 선택 | 이 실험의 근거 |
|---|---|---|
| 한 값이 모든 행을 바꾼다(단위·통화·언어) | 구독 방식은 단순한 쪽을 두고 **구독 위치를 금액 셀 쪽으로 내리거나 행 수를 줄입니다** | 1,000행 단위 전환 INP: 행 구독 192~208 ms, 셀 구독 144~160 ms. 방식 사이 차이는 해상도 안이거나 16 ms 안팎 |
| 일부 행만 바뀐다(선택·펼침·강조), 행이 100개 이상 | **Zustand selector**(또는 상태를 행 안으로 옮김) | 1,000행 선택 INP: Context 112 ms, Zustand 전체 120 ms, selector 64 ms(행 구독). 셀 구독에서는 72~88 ms → 56 ms. 100행에서는 56~64 ms → 48 ms |
| 서로 다른 상태가 한 Context에 섞여 있다 | **Context 분리** | 1,000행 셀 구독의 선택에서 렌더된 컴포넌트가 3,002 → 1,000. INP는 80 → 72 ms로 범위가 겹침 |
| 행이 7개 안팎 | 어느 쪽이든 | 7행의 모든 조건의 중앙값이 48 ms |
| 행이 1,000개 이상 | 구독 방식보다 **렌더 범위 자체를 줄이는 방법**(가상화·페이지 나누기, 미측정) | 같은 단위 전환이 7행 48 ms, 100행 72 ms, 1,000행 200 ms 안팎 |

## 원본 Jonbeo와의 관계

원본 `UnitButton`과 `StockListItem`은 `useUnitStore()`를 선택자 없이 부르며 스토어에는 단위 하나만 있습니다. 이 실험의 **Zustand · whole store · row**에 가장 가깝고, 7행에서 프로덕션 빌드 INP가 48 ms였습니다. Jonbeo MSW 실험의 개발 서버 값(통화 전환 중앙값 314 → 701 ms)은 같은 척도로 비교할 수 없습니다. 개발 서버의 React 개발 빌드, 원본 행의 애니메이션 컴포넌트와 이미지 등이 다를 수 있지만 이 실험으로 분리하지 않았습니다(가설). 이 결과가 말해 주는 것은 하나입니다. 단위 전환처럼 모든 행이 바뀌는 상태에서는 구독 방식을 바꿔도 렌더링 대상이 줄지 않으므로, 줄이려면 행당 렌더 비용이나 행 수를 줄여야 합니다.

## 해석 한계와 미측정

- 합성 데이터와 단순한 마크업(CSS·SVG)입니다. 원본의 `motion`·`AmountTransition`·링크는 없습니다. 행당 비용이 더 크면 구독 위치의 효과도 더 커질 수 있습니다(미측정).
- 한 대의 Mac, 헤드리스 Chrome, CPU 4배 감속입니다. 4배 감속 값은 실제 저사양 기기의 INP가 아닙니다. 실기기·현장 INP는 미측정입니다.
- INP는 로드마다 하나, 조건당 5개이며 8 ms 단위입니다. 8~16 ms 차이는 구분하지 않았습니다. Zustand와 Context의 처리 시간 차이는 일관되게 보였지만 표본이 작습니다.
- 선택 상태는 이 실험이 더한 가정입니다. 선택 외의 상태(필터·정렬·호버)와 여러 상태가 동시에 바뀌는 경우는 측정하지 않았습니다.
- 가상화, `useDeferredValue`·`startTransition`, `React.memo`로 `amount`만 분리하는 등 다른 완화책은 측정하지 않았습니다.
- 원본 Jonbeo 프로덕션 측정(선택 항목)은 하지 않았습니다.
