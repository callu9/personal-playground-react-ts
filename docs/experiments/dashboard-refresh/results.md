# 02. 대시보드 실시간 갱신

[실험 목차](../README.md) · [실험 지침](README.md) · [Playground](http://127.0.0.1:5173/experiments/dashboard-refresh/#playground) · [측정 원본](evidence/)

[비교 조건](#무엇을-비교했나) · [시나리오별 수치](#측정-결과) · [사용 목적별 선택](#사용-목적별-선택)

브랜드 테마 실험의 **Operations overview**를 재사용했습니다. 같은 CSS Modules 테마, 지표 카드, 활동 차트, 상태 분포, 최근 결과 표로 서버의 최신 스냅샷을 보여 줍니다. 화면을 열어 둔 동안 데이터는 계속 갱신되고, 비교에서 바꾸는 것은 고정 폴링·적응형 폴링·SSE의 조회 방식입니다. 기존 작업 상태 실험의 수치는 별도로 볼 수 있습니다. [이전 작업 상태 실험](https://github.com/callu9/personal-playground-react-ts/blob/60c12c6/docs/experiments/dashboard-refresh/results.md)

**이 예시의 일상 운영 화면은 고정 3초를 기본으로 둡니다.** 정상 전달에서 집중 갱신 p95는 2,797ms, 요청량은 20.6건/분/탭이었습니다. 지연이 중요한 관제에서는 SSE가 70ms를 기록했습니다. SSE는 탭별 연결을 유지했고 본문 전송량은 고정 3초의 약 1.9배였습니다. [사용 목적별 선택](#사용-목적별-선택)

## 무엇을 비교했나

| 조건 | 서버 동작 | 화면에서 확인할 차이 |
|---|---|---|
| 평상시와 집중 갱신 | 16초마다 3.8초와 7.8초에 두 번 바뀌고, 9.0~12.5초에는 0.5초 간격으로 여덟 번 바뀝니다. 기본 전달 지연은 40ms입니다. | 평상시와 집중 갱신의 반영 지연, 화면의 최신 상태 유지, 지속 요청·전송량 |
| 느린 응답 | 지표 갱신 일정은 같고 전달 지연은 1,350ms입니다. 폴링은 요청 시점의 최신 값, SSE는 발행된 스냅샷을 지연 뒤에 받습니다. | 응답이 폴링 간격보다 길 때 단일 요청 정책의 영향 |
| 일시 단절 | 피드 생성 후 9.6~13.2초에 한 번, 폴링은 503을 받고 SSE 연결은 닫힙니다. 서버 지표는 계속 갱신됩니다. | 재시도·재연결 이후 최신 상태로 돌아오는 시간 |

서버는 브랜드 실험의 샘플 데이터를 기준으로 총 실행 수, 완료율과 중앙 실행 시간, 오늘 활동량, 최근 5개 결과가 들어 있는 스냅샷을 만듭니다. 도착한 최신 스냅샷 하나로 전체 대시보드를 갱신합니다. 예를 들어 조회 사이에 새 결과 세 건이 생기면 중간 버전은 지나칠 수 있어도 최신 스냅샷의 최근 결과 표에는 그 세 건이 함께 나타날 수 있습니다. 따라서 표의 **미관측 버전**은 소실된 개별 행의 수가 아닙니다.

클라이언트는 숨김 탭에서 연결을 닫고 다시 보이면 즉시 조회합니다. SSE는 새 연결에서 최신 스냅샷을 보내고 이후 변경을 밀어 줍니다. 서버가 낸 모든 이벤트를 저장·재생하는 이력 스트림은 별도 제품 요구입니다.

## 구현과 검증 비용

이전 자동 조회 실험의 공통 스케줄러, SSE 클라이언트와 Vite 모의 API를 재사용했습니다. `Dashboard`와 CSS Modules `ThemeProvider`는 브랜드 테마 실험과 공유합니다. 브랜드 실험은 기본 샘플 데이터를, 자동 조회는 같은 형식의 서버 스냅샷을 전달합니다. 조회 방식을 바꿀 때 같은 피드와 화면을 유지하므로 브랜드 계정·검색·필터를 계속 쓸 수 있습니다.

| 후보 | 후보별 구현 범위 | 변경할 때 확인할 점 |
|---|---|---|
| 고정 폴링 | 공통 GET·폴러 40줄을 재사용합니다. 요청 간격은 1·3·5초입니다. | 주기, 한 번에 하나의 요청, 요청 시간 제한 6초와 0.5~8초 백오프 |
| 적응형 폴링 | 공통 폴러에 새 버전 감지와 4초/1초 정책 15줄을 추가했습니다. | 변경을 관측하면 3초 동안 주기를 줄입니다. 집중 갱신 시작은 직전 4초 주기 때문에 늦게 감지될 수 있습니다. |
| SSE | EventSource 클라이언트 9줄과 서버 스트림 50줄을 사용합니다. 연결당 재시도 지시, 최신 버전, 하트비트, 연결 정리를 유지합니다. | 프록시 버퍼링·타임아웃, 활성 탭당 연결 수, 재연결 정책. 이 로컬 서버는 열린 연결에서 25ms마다 전송할 값이 있는지 확인합니다. |

줄 수는 공통 화면·데이터·라우팅을 제외한 비공백 기준입니다. 세 방식 모두 새 패키지 의존성은 없습니다. 초기 연속 갱신 서버·계측 구현과 첫 빌드는 약 **6분 30초**, 브랜드 화면 연동과 재측정 준비는 약 **5분**이었습니다. 공통 수정·테스트 준비·도구 대기를 포함하고 브라우저 벤치마크 대기는 제외한 벽시계 시간입니다. 후보별 독립 신규 구현 시간은 측정하지 않았습니다. 탐색 시작부터 첫 스냅샷을 DOM에 그릴 때까지의 시간도 화면 준비 지표로 별도로 측정했습니다.

## 측정 방법

- 프로덕션 빌드의 로컬 Vite 미리보기에서 Chrome을 실행했습니다. 모든 표본에서 Grove 계정과 같은 CSS Modules 화면을 사용했습니다. 각 방식에 별도의 피드를 만들고 같은 16초 주기를 두 번, 목표 **32초** 동안 관찰했습니다. 이어지는 세 번째 주기에도 화면은 계속 갱신됩니다.
- 정상은 후보별 3회, 느린 응답과 단절은 각각 후보별 2회입니다. 같은 회차에서 방식별 피드의 탐색 시작 오프셋은 0·0.7·1.3초 중 같은 값을 사용했습니다. 정상에서 고정 3초·적응형·SSE는 같은 피드를 두 탭에서 보는 조건도 한 번씩 실행했습니다.
- **반영 p95**는 서버 기록 시각에서 KPI 버전이 Chrome DOM에 반영될 때까지입니다. 평상시와 집중 갱신을 나눕니다. 미관측 버전은 p95 계산에서 제외하고 별도로 셉니다. 작은 표본에서는 p95가 최댓값인 경우가 있습니다.
- **뒤처진 시간**은 측정 창 중 화면이 서버 최신 버전을 아직 반영하지 않은 시간의 비율입니다. 첫 스냅샷이 표시되기 전 구간도 포함합니다.
- **요청/분/탭**은 스냅샷 GET 및 SSE 최초 연결·재연결을 합산하고 실제 관측 시간으로 환산합니다. **본문 B/분/탭**은 JSON, 실패 응답과 SSE 프레임·하트비트를 포함합니다. HTTP 헤더·TLS, 피드 준비와 통계 조회는 제외합니다.
- **복구 p95**는 단절 종료 때 서버에 있던 버전 이상이 DOM에 처음 나타날 때까지입니다. 서버 CPU, 대량 연결 처리량, 실제 프록시와 브라우저 백그라운드 스케줄링은 미측정입니다. 탭 숨김·복귀는 별도 자동화 테스트에서 가시성 이벤트로 확인했습니다.

### 사용 목적별 선택

**현재 예시의 기본값은 고정 3초입니다.** 운영자가 최신 집계와 최근 결과를 확인하는 용도로 보고, 수 초 지연과 중간 스냅샷 생략을 허용한다고 가정했습니다. 아래 조건은 정상 전달 측정값을 사용한 선택 예시입니다. 실제 화면의 지연 목표와 요청 예산을 따로 정해야 합니다.

| 화면의 목적과 제약 | 선택 | 정상 전달에서 확인한 근거 |
|---|---|---|
| **일상 운영 현황** · 관측 p95 약 3초, 탭당 25건/분, 일반 GET | **고정 3초** | 평상시 2,813ms / 집중 갱신 2,797ms, 20.6건/분/탭. 중간 스냅샷 39/60개는 건너뛰었습니다. |
| **보고용·요청 절약** · 관측 p95 약 4.5초 허용, 탭당 약 15건/분 | **고정 5초** | 13.1건/분/탭, 집중 갱신 p95 4,088ms. |
| **장기 연결 없이 고른 응답 속도** · 평상시·집중 갱신 모두 관측 p95 약 1.2초, 탭당 약 60건/분 허용 | **고정 1초** | 평상시 1,014ms / 집중 갱신 850ms, 58.7건/분/탭. |
| **몰리는 갱신에만 빠른 반응** · 장기 연결이 어려움, 집중 갱신 관측 p95 약 1초와 평상시 약 4초 허용 | **적응형 폴링** | 집중 갱신 802ms / 평상시 3,888ms, 40.0건/분/탭. 새 버전을 만나기 전에는 4초 주기를 사용합니다. |
| **상시 관제** · 낮은 지연 우선, 탭별 장기 연결 운영 가능 | **SSE** | 집중 갱신 p95 70ms, 미관측 0/60개, 정상에서 탭당 연결 1회. 전체 스냅샷을 보내 본문 전송량은 고정 3초의 약 1.9배였습니다. |

반영 p95는 화면에 도착한 버전만 집계합니다. 빠른 반영과 함께 중간 상태 보존이 필요하면 미관측 수치와 재연결 정책도 봅니다. 이 구현의 SSE는 단절 후 최신 스냅샷으로 복구합니다. 추가 전달 지연을 1,350ms로 올렸을 때 SSE의 집중 갱신 p95도 1,381ms였습니다. 단절 복구 p95는 고정 3초 568ms, 적응형 1,588ms, SSE 544ms였으며 후보별 두 번만 관측했습니다.

활성 탭마다 폴링하는 서비스에서는 대략적인 지속 요청률을 활성 탭 수 ÷ 조회 간격(초)로 잡을 수 있습니다. 한 사용자의 여러 탭, 실패 재시도, 실제 응답 시간에 따라 달라집니다. 운영 채택 전에는 실서비스 응답 크기와 서버·프록시의 연결 한도로 확인해야 합니다.
