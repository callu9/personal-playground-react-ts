# 02. 대시보드 결과 자동 조회

로컬에서 고정 폴링, 적응형 폴링, SSE를 구현하고 비교했습니다. Node v24.20.0, Chrome 158.0.8127.37에서 총 24회 실행했습니다. [대시보드 소스](../../experiments/dashboard-refresh/)와 [측정 원본](evidence/dashboard-refresh-benchmark.json)을 함께 볼 수 있습니다.

## 구현과 변경 비용

세 후보는 동일한 React 화면, 버전이 있는 작업 스냅샷, 시나리오, JSON 데이터 구조, 종료 및 탭 가시성 정책을 공유합니다. Vite 개발 서버와 로컬 프로덕션 미리보기에서 같은 작업 API를 실행합니다. 상태는 대기 → 진행 → 완료이며, 같은 실행 URL을 다른 탭에서 열 수 있습니다.

| 후보 | 첫 진행 상태 확인 | 빠른 시나리오 검증 완료 | 이 실험에서 구현한 범위 |
|---|---:|---:|---|
| 고정 폴링 | 24초 | 31초 | 공통 GET 스냅샷과 단일 요청 스케줄러. 주기·타임아웃·백오프·완료 중단 |
| 적응형 폴링 | 12초 | 15초 | 같은 폴러에 대기 4초 / 진행 1초 정책 추가 |
| SSE | 9초 | 15초 | 브라우저 EventSource 구독과 서버의 스트림·재생·하트비트 |

시간은 이 작업에서 기록한 체크포인트부터 첫 상태 표시, 완료·중단 브라우저 검사까지의 벽시계 시간입니다. 공통 준비 구간은 약 **4분 26초**였으며 계획, 공통 서버·화면, 초기 검사와 수정이 포함됩니다. 고정 폴링은 타입 검사 직후 기록을 시작했고, 적응형과 SSE는 준비한 코드를 적용하는 도구 호출에서 기록을 시작했습니다. 뒤의 두 후보의 코드 작성 전 시간을 따로 재지 못했으므로 표를 독립적인 초기 구현 속도 순위로 사용하기 어렵습니다. 후속 시나리오 검사에는 느린 요청과 탭 복귀 17.1초, SSE 단절·재생 15.6초, SSE 두 탭 7.3초가 걸렸습니다. 각 시간에는 시나리오가 진행되는 대기가 포함됩니다.

| 후보 | 후보별 코드와 공통 의존성 | 정책을 수정할 때 |
|---|---|---|
| 고정 폴링 | `polling.ts`의 스케줄러와 공통 스냅샷 API. 후보 코드 1파일·42줄 | 지원 주기는 `contract.ts` 한 곳에서 바꿉니다. 타임아웃·백오프·중복 요청 제어는 공통 스케줄러에 있습니다. |
| 적응형 폴링 | 고정 폴러와 GET API를 재사용하며 `adaptive.ts`에 상태별 정책 1파일·6줄 추가 | 대기·진행 조건과 주기는 `adaptive.ts` 한 곳을 바꿉니다. 진행을 처음 감지하기 전에는 직전 상태의 대기 주기가 적용됩니다. |
| SSE | `sse.ts`와 `server.ts`의 스트림 경로. 클라이언트 13줄과 서버 스트림 62줄 | 브라우저 재연결 간격은 서버의 `retry`, 재생은 서버 커서 처리에서 바꿉니다. 배포 시 프록시, 연결 한도, 인스턴스 간 이력 공유도 확인합니다. |

줄 수는 비공백 기준이며 공통 화면·픽스처·라우팅은 제외했습니다. 세 후보의 패키지 의존성 추가는 모두 0개입니다. 폴링은 완료 후 중단하며, 진행 중 GET은 한 번에 하나만 보냅니다. 응답이 짧으면 목표 시작 간격에 맞춰 다음 요청을 예약하고, 느린 응답이 끝나기 전에는 다음 요청을 시작하지 않습니다. 요청 제한은 6초, 실패 시 재시도는 0.5초부터 최대 8초까지 백오프합니다. 숨김 탭에서는 공통으로 조회를 멈추고, 돌아오면 바로 다시 시작합니다.

SSE는 이벤트 ID를 기준으로 끊긴 뒤 다시 연결될 때 빠진 버전을 보냅니다. 탭을 숨겼다가 새 EventSource를 여는 경우에는 마지막 버전을 전달합니다. 일반 연결 끊김에는 브라우저가 보낸 `Last-Event-ID`를 우선합니다. 이 실험의 스트림은 HTTP 연결을 유지하고 5초마다 하트비트를 보냅니다. 서버는 짧은 가상 타임라인을 스트림마다 확인합니다. 서버 CPU와 대량 연결 처리량은 측정하지 않았습니다. [HTML 표준의 EventSource 재연결과 이벤트 ID](https://html.spec.whatwg.org/multipage/server-sent-events.html)

## 같은 조건으로 측정한 방법

- 정상·느림·단절 시나리오에서 서버는 시작 기준 **4.52·5.35·6.18·7.83·9.89·12.20초**에 같은 6개 스냅샷을 제공합니다. 완료는 버전 6입니다. API 생성부터 총 **19.5초**를 집계합니다. 정상 단일 탭 3회에서는 페이지 연결을 API 생성 뒤 **0·1.10·2.35초**에 시작해 폴링 주기의 위상을 바꿨습니다. 각 회차 안에서는 세 방식에 같은 일정과 지연을 적용했습니다.
- 정상·단절의 전달 지연은 **40ms**, 느린 시나리오는 **1,350ms**입니다. 단절은 작업 시작 기준 **5.8~8.5초** 동안입니다. 폴링은 요청 시점의 최신 스냅샷을 지연 후 받고, SSE는 이벤트 시점에 같은 지연을 적용합니다. 단절 중 폴링은 503을 받고 SSE 스트림은 닫힙니다.
- **반영 지연**은 서버 스냅샷 기록 기준 시각에서 Chrome DOM에 해당 버전의 행이 추가되기까지입니다. p95에는 관측된 버전만 포함하며, 관측되지 않은 중간 버전은 별도로 셉니다. 완료 p95는 3회 중 가장 큰 값입니다. 여기서는 샘플이 작아 p95가 최댓값과 같아지는 경우가 많습니다.
- **요청량**은 스냅샷 GET과 SSE 최초 연결·재연결을 합산합니다. 바이트는 JSON과 SSE 프레임·하트비트 등 응답 본문을 기준으로 계산합니다. 작업 생성·통계 조회, HTTP 헤더와 TLS 비용은 집계에서 제외했습니다. 요청/분은 19.5초 작업 구간을 환산한 값이며 준비와 완료 후 관찰 시간이 포함됩니다. 운영의 지속 요청률은 별도 산정합니다.
- Chrome에서 각 후보는 별도의 브라우저 컨텍스트와 같은 가상 화면 크기를 사용했습니다. 정량 실험은 전 구간에 탭이 숨겨지지 않았는지 검사합니다. 숨김·복귀 회귀 테스트는 가시성 이벤트를 모의했으며 브라우저의 실제 백그라운드 타이머 제한은 미측정입니다.

## 폴링을 선택할 조건

제품 SLA와 운영 부하 예산은 주어지지 않았습니다. 아래는 정상 시나리오의 측정값을 목표에 대입한 예시입니다.

- **고정 3초**는 중간 진행 상태를 건너뛰어도 되고, 완료 표시 p95 **2.5초**와 탭당 **20건/분** 수준의 작업 예산을 함께 만족해야 할 때 검토합니다. 이 샘플은 완료 p95 **2,105ms**, 평균 **17.4건/분**이었습니다.
- **고정 5초**는 완료를 약 **3.5초** 내에 확인하는 것으로 충분하고 작업당 요청을 더 줄이는 경우에 맞습니다. 이 샘플에서는 완료 p95 **3,325ms**, 탭당 **12.3건/분**이었습니다.
- **적응형**은 대기 구간의 요청을 줄이면서 진행 시작 이후 빠르게 갱신하고 싶을 때 검토합니다. 이 샘플에서 고정 1초 대비 요청률은 **43% 감소**했고, 완료 p95는 **346ms**였습니다. 중간 버전 7/18개는 화면에 나타나지 않았습니다.
- **SSE**는 빠른 전달과 단절 후 모든 버전의 재생이 필요하고 장기 연결을 운영할 수 있을 때 선택할 근거가 있습니다. 정상 반영 p95는 **75ms**였고, 단절 뒤 **437ms**에 최신 상태를 복구했습니다. 두 탭 실험에서는 동시 스트림 2개를 사용했습니다.

실제 환경의 주기는 **완료 반영 목표와 API 요청 예산을 먼저 정한 뒤**, 두 조건을 충족하는 가장 긴 간격으로 선택합니다. 요청이 겹치지 않는 정상 상태에서 활성 탭 수를 주기(초)로 나누면 대략적인 초당 요청량을 계산할 수 있습니다. 예를 들어 활성 탭 1,000개가 3초마다 요청하면 약 333건/초입니다. 탭 여러 개, 작업 수, 동시 재시도, 지터, 완료 후 중단이 이 추정에 영향을 줍니다. 응답이 느리면 유효 조회 간격이 길어지므로 느린 API에서도 검증합니다.

빠르게 변하는 **최신 상태만 표시**하면 고정 폴링이 단순합니다. 대기가 길고 진행 구간의 표시 속도가 더 중요하면 적응형 폴링을 검토합니다. 적응형도 진행 시작을 대기 주기만큼 늦게 알아차릴 수 있습니다. **모든 버전 전달**이 제품 요구라면 SSE 재생 또는 커서를 지원하는 증분 조회가 필요합니다. 이번 폴링은 최신 스냅샷 조회 방식입니다.

운영 판단에는 인증 만료, 프록시 버퍼링·연결 제한, 데이터 및 이력 저장소, 실제 서버 비용이 남습니다. 기존 서비스에서 폴링을 선택한 당시 이슈나 PR은 제공되지 않아 이번 결과를 과거 의사결정의 근거로 사용하지 않습니다.

## 재실행

```sh
npm run dev
npm test
npm run build
npm run measure:refresh
```

개발 서버의 첫 화면에서 **Dashboard auto refresh**를 엽니다. 측정 명령은 로컬 미리보기 서버를 열고 `test-results/dashboard-refresh.json`에 원본을 저장합니다. 숨김·복귀 검증은 `npm test`에서 실행합니다. 지정된 `callu9ine` Chrome 프로필의 로컬 미리보기에서도 단절 시나리오를 실행해 SSE가 완료 상태와 초기값을 포함한 0–6 버전을 표시하는 것을 확인했습니다.
